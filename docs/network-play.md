# 联网对战施工记录

联网使用两个真实游戏引擎和原游戏协议。AI 只控制自己的座位，游戏不暂停等待 Python 推理。赛制由原游戏执行，包括三局两胜、局间过渡和比赛后的菜单流程。完整验收要求见[训练与交付验收](training-acceptance.md)。

## 统一实时入口的施工状态

新的原生实时通道已接入建房端和加入端。它按完整游戏帧发布状态快照，并接收带绝对到期帧的
本地按键。写入方停止工作或写入到一半退出时，游戏线程不会等待。读取方落后超过历史容量时
明确报错，不能静默丢失神 AI 所需的逐帧输入。学习与规则策略的统一 Python 入口仍在施工，
下文旧入口的角色与拟人模式限制尚未全部移除。

`NetworkGame` 现须明确指定是否绘制。关闭战斗绘制保留原时钟、原网络协议和菜单流程；
原有限速关闭选项仍只用于离线训练。`tools/netplay.py` 的现有工作进程继续开启绘制。

本轮真实引擎诊断使用角色 6（蕾米莉亚）和 19（诹访子），由测试程序操作两个独立客户端。

## 已实现的连接入口

`native/SokuRLBridge/NetworkStart.cpp` 在标题菜单完成展开后，通过 SokuLib 的原生连接菜单建房或加入房间。它不调用等待场景切换的阻塞函数，不控制比赛输入，不改双方角色，也不修改游戏赛制。

下列环境变量是原生模块与启动进程之间的参数。正式 Python 入口是 `tools/netplay.py`，由专用工作进程设置这些变量：

| 变量 | 含义 |
| --- | --- |
| `SOKURL_NETWORK_ROLE` | `host` 建房，`join` 加入；变量不存在时不启用此模块 |
| `SOKURL_NETWORK_PORT` | 必须明确给出 1–65535 的十进制端口 |
| `SOKURL_NETWORK_ADDRESS` | 加入时必须提供 IPv4 地址 |

网络启动与离线 `SOKURL_VS_BOOTSTRAP=1`、解除限速 `SOKURL_UNLIMITED_PACING=1` 冲突时，模块加载失败。输入错误也会直接拒绝加载。网络入口不开放旁观者。

自动连接入口明确选择本地键盘设备。它没有人工按键来设置输入设备编号，不能沿用未初始化的手柄编号。人工启动、未设置 `SOKURL_NETWORK_ROLE` 的游戏不受此设置影响。

标题就绪条件来自原版 1.10a 的 `Title::onProcess`：菜单状态非零且 `Title + 0x68C` 的菜单展开计数至少为 16，并且没有活动子菜单。只有原函数仍返回标题场景时才创建连接菜单。模块只发起一次连接；连接失败由原游戏菜单呈现，不在后台自动重试。

## 联网状态通道

提交 `605ea33` 增加独立的 `Local\SokuRLNetwork_<pid>` 共享内存。原生 `NetworkState` 与 Python `tools/network_state.py` 共同定义版本 1、13272 字节的布局。写入前后更新序号，读取端只有在序号一致且不处于写入阶段时才接受快照，并检查帧身份和原始状态校验值。

这个通道只读提供最新状态，不暂停游戏，也不允许离线联合动作、暂停或重置命令控制联网比赛。字段含义如下：

| 字段 | 含义 |
| --- | --- |
| `scene`、`local_seat` | 原游戏场景，以及主机 0、客户端 1 的本地座位；其他场景无座位 |
| `match` | 每次从非网络战斗场景进入网络战斗时增加，局间过渡不增加 |
| `updates` | 当前比赛已完成的 `BattleManager::onProcess` 调用次数；不是网络包编号 |
| `scores` | 原游戏双方角色的已赢局数 |
| `raw.roundId` | 原游戏的局编号，与整场比赛编号分开 |
| `raw`、`render` | 原始状态和用于可见性过滤的渲染属性；不能直接当作拟人策略观测 |

这里的 `connected` 表示桥接模块仍存活，不表示远端玩家仍在线；比赛中断需要结合场景变化与进程状态判断。此最新快照通道不保证消费者读到每个更新，也不包含图像像素。双方血量归零不会使读取端自动结束比赛。

本版本 DLL SHA-256 为 `b0086bea951d31f43dfffda074fcd1dddd45a0fe1d60357ca5d1fe385ac4075c`。服务器全量检查 **206 项通过、1 项跳过、2 个参数子检查通过**，耗时 **29.76 秒**；跳过项依赖 Windows 原生窗口接口，另有 4 条已有依赖提醒。

`network-state` 双引擎诊断成功，耗时 **84.83900000154972 秒**。双方各读取 26 个快照，更新计数达到 316，比赛编号 1、局编号 0、比分 0:0、血量 10000:10000。`peer-comparison.json` 对更新编号 14、25、144、186、294、316 进行比较：排除主客不同的场景、模式及相应校验值后，其余全部原始状态字节和比分一致。这是无操作联网战斗的状态采集证据，不是完整逐帧、局间或三局两胜验证。

## 本地战斗按键调度

`NetworkInput` 与 `tools/network_runtime/input.py` 使用独立的 104 字节请求映射。每个请求携带比赛编号、局编号、感知更新编号、目标注入编号、八个逻辑按键及保持时长。目标注入编号固定为感知编号加 5；相邻请求的感知编号至少相隔 3 次更新，实际注入也至少相隔 3 次更新。原游戏跳过输入处理时机会增加实际延迟。保持时长必须明确给出，范围为 1–120 次更新。请求过期、比赛或局号不符、输入非法时返回明确拒绝结果。更新后的请求必须等待上一请求确认，不能覆盖尚未读取的请求。

离开战斗、局号变化或任一角色血量归零时清除待执行动作和保持按键。`release()` 是需要确认的释放控制命令，关闭共享内存本身不代表游戏已收到释放命令。`latest_injection()` 只报告最近一次注入的请求编号及更新编号，不表示角色已执行动作，也不是完整事件历史。

最初的 `0eee6ce` 仍向选人键盘注入，真实诊断中请求获准且注入编号正确，但双方角色输入均为零。把提交时间从第 184 次更新推迟到至少完成 600 次更新后仍失败，排除了开场时机的解释。原游戏在加载阶段通过 `0x43F045/0x43F08A` 将本地发送输入指针切换到玩家配置对象；发送函数 `0x454CA9/0x454CCB` 从该对象读取编码按键。提交 `b3ea9dd` 因此改为匹配当前本地发送输入对象，保持网络接收对象不变。

修复 DLL SHA-256 为 `f26bb0126fa8f4cf352e27954711238e6f0219a123fb3208a69c08e85a2cb39c`。`network-profile-input` 真实检查成功，耗时 **90.8329999987036 秒**：主机感知编号 180，目标注入编号 185，实际注入编号 185；随后主机角色从 x=480 移至 x=750，客户端角色按键始终为零。双方各采集 62 个快照，22 个共同更新编号的原始战斗状态一致（排除场景、模式及对应校验值）。过期请求返回 `late`，错误比赛编号返回 `wrong_round`，释放命令得到确认。

## 整场比赛与再战

`src/soku_rl/play/match.py` 的 `MatchLifecycle(wins_required)` 消费与传输方式无关的 `MatchState`，分别报告开赛、开局、比分变化、整场结束和比赛中断。规定胜局数必须明确提供；原版三局两胜使用 2。这个模块观察原游戏结果，不改变原游戏赛制。`round_started` 通知调用方按策略约定处理小局记忆边界；`can_act` 只在双方血量仍大于零且整场未结束时为真。单回合血量归零不产生整场结果，离开比赛而未观察到获胜比分记为中断，不记为输局。

真实 `network-match` 检查使用双方本地按键，未修改血量或比分，依次完成 **0:0 → 1:0 → 1:1 → 2:1**。双方比赛编号始终为 1，局编号依次为 0、1、2。双方分别采集 **2681、2737** 个快照，**390** 个共同更新编号的战斗状态一致，比较时排除场景、模式及相应校验值。`match-analysis.json` 确认每端恰好产生三次开局及一次整场结算。

该检查的整体 `result.json` 为失败：1200 秒内未进入下一场。比分到 2:1 后，战斗输入接口拒绝血量归零后的按键，赛后流程无法继续。这份记录证明完成三回合，不证明再战通过。

## 有限长度的完整状态历史

提交 `2f8a75f` 增加 `Local\SokuRLNetworkHistory_<pid>` 和 `NetworkHistoryClient.read_after(cursor, timeout)`。原生端保留最近 256 条记录，每次完成战斗管理器更新以及每次场景变化都追加记录。记录序号跨回合、跨比赛递增，不能与游戏帧号混用。读者获得下一游标及有序快照；没有新记录时返回空批次，记录被覆盖时抛出 `BufferError`，生产端正常关闭时抛出 `EOFError`。写入不会等待读者，也不改变游戏速度。

消费方应在进入比赛前开始读取。它必须处理所有记录，并在新回合重建策略状态；数据丢失必须中止当前推理记录，不能假装帧历史完整。历史仍是内部原始数据，策略输入需要经过可见性过滤。相机属性与画面时序的核对尚未完成。

## 训练与实时推理的共享观测

`ObservationHistory` 现在供训练环境和 `LivePolicy` 共用，按每个连续游戏帧堆叠公开观测；缺帧直接报错。`LivePolicy` 每个回合重新创建策略实例，并通过同一个 `LearningInterface` 和 `LearningEpisode` 生成相对位置、自身动作历史及动作编号映射。它只在决策边界调用策略一次。原游戏回合超过训练时限后，经过时间特征保持在上限，不能据此结束真实比赛。

## 正式策略入口

`tools/netplay.py` 使用 `config/netplay.yaml`，与训练共用 Hydra 配置空间。运行顺序是加载模型、在指定设备上预先执行模型以初始化计算内核、启动网络游戏，再持续读取完整状态历史。[本机对战入口](local-play.md)使用 CPU，并启动人类玩家的第二个游戏。运行模块分工如下：

| 模块 | 职责 |
| --- | --- |
| `WorkerConnection` | 有超时限制的本地父子进程通信 |
| `network_worker.py`、`NetworkGame` | 拥有一个游戏进程，读取公开观测，只提交本地输入；不提供离线重置和暂停 |
| `MatchLifecycle` | 区分局、整场比赛、再战和中断 |
| `LivePolicy` | 复用训练观测和动作映射，每局重新建立模型记忆 |
| `run_session` | 按顺序处理状态与结果，记录动作，完成指定场数后退出 |

必须明确配置以下字段：

- `runtime.command`：工作进程启动命令列表，最后一个参数为 `tools/network_worker.py`；Linux 使用 Wine 启动脚本，Windows 使用项目 Python。
- `runtime.cwd`：安装游戏及桥接模块的仓库目录。
- `candidate.policy`：原训练模型使用与评测相同的模型描述；CPU 导出模型使用 `kind: onnx_recurrent` 和指向 `policy.json` 的 `path`。
- `episode` 和 `wrappers`：必须与模型训练配置逐项一致。当前联网入口只接受公开状态、每 3 帧决策、5 帧注入延迟。
- `device`：执行推理的设备；本机导出模型必须使用 `cpu`。
- `network.role`：`host` 建房或 `join` 加入；`network.address` 是 IPv4 地址，`network.port` 是端口。

`network.automate_menu=false` 时，玩家手动选人并确认赛后对话；设为 `true` 时，模块只发送本地确认键，不更改角色或赛制。`session.matches` 按整场比赛计数，默认 2 场；`session.timeout` 是整个会话的秒数上限。每场由原游戏执行三局两胜，原训练的单局时限不会结束网络比赛。

运行结果目录保存解析后的配置、模型指纹、源码和游戏文件指纹、工作进程日志、游戏进程编号、压缩事件记录和最终结果。`events.jsonl.gz` 中的动作请求、原生注入事件、引擎读取到的按键分别记录。渲染属性和引擎按键仅用于核查，不进入策略输入。断线、状态历史被覆盖及无效输入产生失败结果。因实时游戏继续推进而发生的过期或跨局请求记录后丢弃，不算作已执行动作，也不算败局。

入口提交 `7072ebd` 的全量测试为 **223 项通过、1 项跳过**。`policy-bo3-v1` 使用两个真实引擎和两个 GPU 模型实例，双方加载拟人循环 PPO 第 131072 次决策检查点。两端各提交 1888 次动作，请求均获接收；原游戏完成第一局，比分变为 0:1，并开始第二局。最后成功记录为比赛 1、局 1、更新 5940。

随后两端均因 `renderer object metadata overflow` 失败，主机耗时 **671.6709018014371 秒**，客户端耗时 **628.1111692320555 秒**。这次运行没有完成要求的两场比赛。失败结果和事件记录已保留；这个版本没有保存失败帧的完整渲染对象，因此尚不能区分对象数量超过 64、不可见对象占用容量或采集列表不一致。后续版本在观测编码失败时保留原始状态与渲染属性，继续定位。此次复用了前次正常退出后的端口并成功进入战斗，端口正常复用已得到实机证据。

## 逐请求输入记录

`Local\SokuRLNetworkInputEvents_<pid>` 是独立的只读历史映射。32 字节头后保留 256 条、每条 48 字节的记录；记录包含请求编号、命令类型、比赛和局编号、保持时长、感知编号、目标编号和事件发生编号。原生端分别记录接收结果、实际注入、错过注入时机和局间取消。收到 `accepted` 不等于已注入；`injected` 也不等于角色已经执行动作，后者还受原游戏网络缓冲和角色状态影响。

`NetworkInputEventsClient` 与状态历史共用稳定快照读取逻辑，历史被覆盖时报错。战斗请求先获接收、随后因原游戏跳过输入边界而过期时，推理会话也必须失败。关进程时尚未注入的请求记为取消，其事件编号为 `NO_FRAME`，不能当作实测游戏帧。

事件记录版本的 MSVC x86 构建已通过，DLL SHA-256 为 `e57aea67f8e9fd10152bcfd4ce20d62694ad9ac9b3200e42eb39ebafa445c753`。隔离工作区的全量测试为 **226 项通过、1 项跳过、2 个参数子检查通过**，耗时 **39.52 秒**，另有 4 条已有依赖提醒。`policy-bo3-v2` 记录到客户端请求 70 在更新 208 获准，目标为 213，但下一次原生输入处理已到 214，旧调度器将其记为过期。

`NetworkInputSchedule` 因此改为：在不早于目标的下一次可用输入处理时机注入；同一时机积压的旧意图记为 `superseded`，只注入最新到期意图，不能连发补做旧动作。原生测试验证真实的 208、213、214 序列，以及实际注入间隔、按键到期和局间取消。曾发现增量构建遗漏新增头文件依赖，后续已增加明确依赖并完整重建；旧 DLL 的失败不能当作新调度器的测试结果。
