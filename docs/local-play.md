# 本机 CPU 人机对战

推理和两个游戏进程都在同一台 Windows 机器运行。模型使用 ONNX Runtime 的 CPU 执行器，一个计算线程，不加载 PyTorch，也不请求远端推理服务。两个游戏仍通过本机回环地址连接，遵守原游戏的网络协议与三局两胜赛制。

## 启动入口

配置完成后，双击 `scripts/play-local.cmd`，输入玩家座位 `1` 或 `2`，再输入对手名称 `ppo` 或菜单列出的规则策略名称。请在标题为 `SokuRL - Player` 的窗口中选人和操作，按键沿用游戏的玩家配置。

玩家选 1P 时，玩家窗口先建房，AI 加入成为 2P 并选择灵梦；玩家选 2P 时，AI 先建房成为 1P 并选择魔理沙。AI 用原游戏菜单按键选择角色；战斗开始时再次校验角色，选错就报错。人类玩家自行选人、确认赛后对话，AI 自动确认自己的菜单。

也可以直接运行 `scripts/play-local.cmd -PlayerSeat 2 -Opponent ppo`，或 `scripts/play-local.cmd -PlayerSeat 1 -Opponent community_combo`。Python 入口使用同一套 Hydra 配置：`human.seat=1` 指定玩家 1P；`+play_opponent=rule play_rule=rush` 指定规则对手。

当前模型、逐个规则的独立测试成绩和可加载策略范围见[当前试玩策略](current-play-policy.md)。

一次会话最多运行 100 场，或运行 7200 秒；这两个限制由 `config/play_local.yaml` 指定。一方先赢两局才计为一场。局间清除 AI 待执行按键，重建模型记忆。训练中的单局时限不会提前结束真实比赛。

在原游戏中返回选人会放弃当前场，清除 AI 记忆并允许重新选人；放弃的场次不计胜负。赛后确认异步等待，玩家停留不会触发两秒超时。关闭游戏会结束当前会话，并关闭它启动的游戏进程；结果记录 `termination: game_closed` 及已完成的实际场数，不把提前退出记成完成全部 100 场。

需要项目的 Python 环境、`rl` 和 `play` 依赖、原版 1.10a 游戏及匹配源码的 Win32 桥接模块。机器路径和模型路径写入不提交的 `config/local/play.yaml`：

```yaml
# @package _global_
candidate:
  name: human-cpu
  policy:
    kind: onnx_recurrent
    path: C:/Models/human-cpu/policy.json
runtime:
  command:
    - C:/Projects/SokuRL/.venv/Scripts/python.exe
    - tools/network_worker.py
  cwd: C:/Projects/SokuRL
network:
  port: 10811
```

模型目录必须同时包含 `policy.json`、`actor.onnx` 和 `training.yaml`。加载时核对模型文件校验值、观测尺寸及训练配置。默认使用学习包装配置；如果模型采用不同包装，必须明确配置并通过一致性检查。

## 实时控制

AI 每 3 个游戏更新产生一次决策，`latency_frames=5`。按键不会早于观测后的第 5 个更新注入。原游戏有时在两次输入处理之间推进多个更新，这会增加实际注入延迟；不能把配置值称为完整端到端延迟。实际注入之间至少相隔 3 个更新。

Windows 调度导致观测积压时，程序仍依次处理每帧观测，只对最新决策时机推理。已过期的提交或跨局提交会记录并丢弃，不停止游戏。无效输入、历史记录丢失和采集错误仍会明确报错。

内部渲染信息最多采集每方 1024 个候选对象，排除无绘制数据、全透明和中心在画面外的对象。可见性计算完成后，每方公开状态保留按屏幕横坐标、纵坐标和朝向排序的前 64 个可见对象。隐藏对象不占模型槽位；遮挡计算先使用全部已采集对象。模型输入尺寸保持不变。此规则只描述有限状态观测，不是逐像素分割；超过内部采集上限仍会报错。

渲染信息扩大后，图像共享映射为版本 3，网络状态与状态历史映射为版本 2。它们与原有控制 ABI 8 分开。部署必须同步 Python 和 DLL，旧版采集记录不能冒充新版验证结果。

## 已测结果与待验收项

拟人循环 PPO 第 131072 次决策模型已导出。连续 2048 次决策与原模型核对，动作概率最大绝对误差为 `2.9802322387695312e-08`，循环状态比较通过。

本机 CPU 的 4096 次推理检查通过：中位数 `0.58445 ms`，95% 分位数 `1.664225 ms`，99% 分位数 `2.696845 ms`，最大值 `6.5446 ms`。该检查使用符合输入尺寸的合成观测，不能替代游戏中的整场延迟检查。

`cpu-local-bo3-v5` 已通过两个 CPU 模型、两个真实引擎的完整对战：先以 0:2 结束第一场，再完成 2:1 的第二场，共五局。两端结果均为成功。双方分别完成 8600、8601 次决策，实战推理的 99% 分位数分别为 `4.3946 ms`、`4.0784 ms`。两端 25799 个共同战斗更新中的比分、局号、引擎按键和渲染属性全部一致。

玩家入口也已实际启动两个窗口，使用本机回环地址连接并进入战斗。检查时，人类一侧的桥接控制请求数为零，AI 只控制自己的座位。人工操作进一步暴露了赛后等待超时和返回选人被误当作断线的问题，两处已修复。包含正常退出和取消比赛处理的全量检查为 239 项通过、1 项跳过；人工停留与关窗的专项实机检查尚未全部完成。详细证据及剩余可见性检查见[联网施工记录](network-play.md)。

每次运行保存配置、模型指纹、游戏进程编号、压缩事件日志及结果。事件记录区分模型请求、原生接收、实际注入和引擎读到的按键，供检查延迟和中断原因。
