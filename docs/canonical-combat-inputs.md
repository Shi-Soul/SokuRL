# 以当前自身朝向统一几何输入

[相对朝向动作头](facing-action-head.md)只排列动作输出，输入仍保留绝对
方向信息；该候选完整 BC 和 PPO 均未取得纯 God 胜局。本实验进一步统一
神经网络的几何及输入历史表示，检验双座位共享是否受益。它不是重跑原
动作头实验，也不把方向分布更均衡当作策略更强的证据。

`CanonicalCombatFeatures` 复用原地址不变编码器及全部可训练层，搭配现有
`FacingRecurrentActorCriticPolicy`。只在神经网络入口转换张量，不修改游戏、
规则 AI、原始观测、回放或 PPO 保存的绝对动作。输入仍为 590890 维，
完整 576 指令、逐帧决策、零延迟、完整对象列表与对象顺序保持相同。

## 变换范围

以最新历史帧中自身 `dir` 为参考，朝左时对所有历史帧执行下列镜像，朝右
时使用原几何数值。所有历史帧共用当前参考，避免把过去发生的转向抹掉。
`arena_width=1280` 是显式模型配置，与项目既有坐标和镜像定义一致。

- 双方 fighter 及双方全部在场对象：`x → 1280-x`、`xspeed → -xspeed`、
  `dir → -dir`；竖直分量保持原值。
- 每个有效碰撞框 `(left, top, right, bottom)` 转为
  `(1280-right, top, 1280-left, bottom)`，保持框和对象的顺序。
- 双方原始按键历史交换左/右持续计数；学习接口附加的每个历史指令反转
  水平分量，其他方向和六个按钮位不变。
- 零填充历史、未使用对象槽及无效碰撞框不转换。世界字段、动作/动画编号、
  旗标、角色、卡牌、技能、特殊状态等其余字段保持原值；地址仍由既有编码器屏蔽。

字段依据共享 `memory_schema.py`、编码器和 `tools/game_runtime/privileged.py`：
碰撞框已是世界坐标，`keys` 中第 2/3 个分量是左/右持续计数。另核对已有
SokuLib 的 `CharacterManager.hpp`：特殊字段包含卡牌数量、效果/召唤冷却等，
不能将它们当作坐标一并反转。本实验定义的是上述观测变换，不宣称已经
证明所有角色机制或任意实际游戏轨迹具有严格物理镜像对称。

几何值用 float64 做变换，随后按相同解码权重重新拆成两个 float32 分量，
保留直接转为单个 float32 会丢掉的相减残差。两朝向都采用同一表示，避免
原来的拆分形式泄露方向。该转换只供神经网络使用；原始观测字节不变。
合成细小坐标检查覆盖这一精度问题；网络矩阵计算仍可能有常规浮点舍入。

共享 PPO 工厂要求此编码器与 `own_facing` 动作头一起使用，错误搭配会
立即报错。BC、PPO、BR、IPPO、PSRO 和 ONNX actor 使用相同编码器；没有
另写 PPO 更新。检查点保存模型配置；原编码器权重不能静默跨架构加载。
NFSP 原有的前馈 reservoir 限制不在本次修改范围内。

## 有限实验

`pretrain_recurrent_canonical_demonstrations` 使用原 48 局教师数据、相同
训练/验证划分、seed=341729、20 epoch、batch=256、sequence_length=64、
学习率 3e-4、value_coef=.5、action_change_weight=1。固定魔理沙对灵梦，
7200 帧上限，按完整验证 NLL 选 best。该模型不加载失败的 PPO 检查点。

先核对共享工厂创建的全部初始参数与原 BC 逐位相同、Adam 为空、PPO
计数为零，再提交代码并启动完整 BC。预训练结束后执行原 8 个世界种子 ×
双座位的完整 16 局纯 God 评测，记录双方掉血、符卡和逐帧输入，并对照
原 BC 与仅相对动作头 BC。它们是开发网格，不是独立最终测试。
不因离线准确率或对称性单元测试通过而自动追加 PPO；实战结果决定后续预算。
后续 PPO 继续复用长期 EMA 自适应 uniform / 神 AI 课程，不增加固定 stage。

## 几何变换的局部性能诊断

训练期间在空闲 GPU 5 单独检查对象压缩原型：先提取所有在场对象，执行
同一个几何变换，再写回原槽位；其余槽位复制原值。未修改生产模块、
当前训练进程或检查点，也没有减少在场对象数量或改变顺序。

固定初始权重，从原教师数据前四个 episode 各等距抽取 64 帧，检查
batch=1/8/64/256。每种批量的规范化输入、完整特征输出及特征参数梯度
都逐位相同。每项预热 3 次、同步 CUDA 计时 9 次，以下为中位数：

| batch | 原特征前向 ms | 压缩原型前向 ms | 原前向+反向 ms | 压缩前向+反向 ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.340 | 3.905 | 6.869 | 5.362 |
| 8 | 4.390 | 4.634 | 6.046 | 6.191 |
| 64 | 10.062 | 6.525 | 11.588 | 7.969 |
| 256 | 31.412 | 13.094 | 33.206 | 14.445 |

batch=256 的样本平均每名玩家 1.666 个在场对象、最多 29 个；batch=1
样本没有对象。这些观测未覆盖满对象列表，单个小批量结果不能推广到
所有对局。较大批量有优化空间，batch=8 反而略慢；正式采用前需覆盖空
对象、满对象、历史 padding 和不同设备，并验证完整更新及实际吞吐。
同期 BC 使用另一张 GPU，但主机负载及温度未受控；上述不是端到端
训练加速或策略强度结论。

退出 0 的脚本/日志为 `.dev/profile-canonical-compaction-20261003.{py,log}`；
`logs/diagnostics/canonical-compaction-profile-20261003/summary.json` 保留各次
计时、样本索引、数据哈希和检查点身份。当前 BC/后续实战仍使用原实现。
